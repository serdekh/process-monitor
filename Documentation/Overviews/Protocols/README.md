## Description

The overall architecture of the project involves two applications (namely: a **_Server_** and a **_Client_**) communicating with each other using the **Named Pipes API (or NPFS)** form of **IPC**.

However, this is not enough to make the communication work well. Both the **_Server_** and the **_Client_** have to define how to interpret the bytes which they send or receive. Some sort of a language or a protocol. 

For this project specifically, we define a minimal version of the **HTTP REST API** protocol. 

It assures that both sides use the **JSON** file format as a payload type. And this file is also obliged to have certain properties depending on the message type. More on that later.

Every message in the protocol falls into one of the three following types:

- **_CommandRequest_**
  - Gets created by the **_Client_** side and is sent via the **_Commands_** pipe to the **_Server_**.

- **_CommandResponse_**
  - Gets created by the **_Server_** side and is sent via the **_Commands_** pipe to the **_Client_**.
  Right now it is only generated in response to the **_Client_**'s requests.

- **_TelemetrySnapshot_**
  - Gets created by the **_Server_** side and is sent via the **_Telemetry_** pipe to the **_Client_**. 
  The pipe is write-only for the **_Server_** and read-only for the **_Client_**.

For each type there is a specific file structure. Below are all of them with a description:

### CommandRequest
```json
{
    "version": number,
    "requestId": number,
    "type": string,      # in this case it's "CommandRequest" 
    "method": string,    # mimics the REST API verbs
    "route": string,
    "body": object       # optional. Depends on the request method and route
}
```

### CommandResponse
```json
{
    "version": number,
    "requestId": number,
    "type": string,       # in this case it's "CommandResponse" 
    "statusCode": number, # mimics HTTP status code
    "body": object        # optional. Might contain warnings 
}
```

### TelemetrySnapshot
```json
{
    "version": number,
    "type": string,               # in this case it's "TelemetrySnapshot" 
    "timestampUtc": string(Date),
    "body": object                # the actual telemetry message
}
```

Every message shares two properties: _version_ and _type_.

The _version_ property tells the handler which API version is used. Right now it is mainly ignored because there is no stable release and there is plenty of room for experimenting with the protocol configuration. However, it will become a significant part in the future to differentiate various intents and maintain backward compatability. Thus, it is already defined. 

The _type_ property is the key property for the consumer and the sender to identify what kind of message it is. It can never be optional. Its value is also defined as a string that can take one of the following values: "CommandRequest" "CommandResponse" and "TelemetrySnapshot".

The _requestId_, found in both the **CommandRequest** and the **CommandResponse** types, uniquely describes the request sender. It gets generated by the **_Client_** and the **_Server_** attaches it to the response message to give an identifier as to whom this response is actually created for. 

The _route_ property, found in the **CommandRequest** message, describes what resource is being targeted. Currently, the only supported resource is **"monitoring"** but in the future, when the configuration system gets improved, the **"settings"** resource will also become available. 

The _method_ property, found only in the **CommandRequest** message, describes the 'verb' or the 'action' that needs to be performed on a resource specified by the _route_ property. It is a string and it takes one of the following values: "post", "delete", "put" (case insensetive).

Here is a table that describes the built-in functionality for the **Commands** module in the **ProcessMonitor.Backend** project:

| Method (string)  | Route (string) | Body (.json) | Description (.txt)
| ------------- | ------------- | ------------- | ------------- |
| "POST"  | "monitoring"  | {"processId": number } | Sets a new processId value to the global state object and starts monitoring the system events for that id |
| "delete"  | "monitoring"  | - | Sets 'null' value to the global state of the **_Server_** and stops further event collections |

The _statusCode_ property, found only in the **CommandResponse** message, describes the result of parsing and executing the incoming request. It uses the same values for the code as in the **HTTP** protocol. Here is a table of all the codes which are supported by the current **ProcessMonitor.Backend** implementation:

| Status code (number:int) | Description (.txt)           |
| ------------------------ | ---------------------------- |
| 200                      | Success                      |
| 400                      | Invalid Request              |
| 404                      | Process/Resource not found   |
| 409                      | Monitoring is already active |
| 500                      | Internal error               |

This is the entire protocol the current implementation is using. For now it is going to be like that for a while because it is stable however the specifics might change, especially about routing because of its functional limitation.
